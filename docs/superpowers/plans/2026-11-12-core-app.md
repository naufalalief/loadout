# Core Download Manager App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Windows, Tauri/Rust desktop app: a tray-resident download manager with a multi-segment HTTP download engine (pause/resume/retry/per-download speed limit), a queue, a simple UI, and a local HTTP endpoint ready for the browser extension (built in a separate plan) to hand off captured links to.

**Architecture:** Rust backend (`src-tauri/`) owns all download logic in a `download` module (engine, limiter, queue, persistence) behind a `QueueManager` that the Tauri command layer and a local Axum HTTP server both call into. The frontend (`src/`, plain HTML/CSS/JS, no framework) polls Tauri commands to render the queue and exposes an add-download dialog and settings screen. The app launches hidden to the tray and auto-starts with Windows; the main window opens on demand.

**Tech Stack:** Tauri 2, Rust (tokio async runtime, reqwest for HTTP, axum for the local server, serde/serde_json for persistence, uuid, rand, tauri-plugin-autostart), vanilla HTML/CSS/JS frontend, wiremock for Rust integration tests.

**Spec:** `docs/superpowers/specs/2026-11-12-download-manager-design.md`

## Global Constraints

- Windows only for this plan; no macOS-specific code (spec: "macOS build... Explicitly deferred").
- Per-download speed limiting only — no global/shared bandwidth cap (spec: user's explicit v1 priority call).
- App lifecycle is tray-resident, auto-starting with Windows; main window opens on demand, not on every launch (spec: user-confirmed decision).
- Any cookies/headers a download carries are held in memory for that download's lifetime only — never written to disk or logs (spec: privacy baseline tied to the handoff-payload decision).
- No licensing/activation/DRM scheme of any kind (spec constraint: this is what drove the user off IDM).
- Multi-segment downloads must degrade to a single-stream download when the server doesn't support range requests, rather than failing (implied by "multi-segment... for speed" being a means, not a requirement every server must satisfy).

## Review Focus

- Server doesn't support HTTP Range requests → engine must fall back to a single-stream whole-file download instead of erroring out the whole download.
- Network drops mid-segment → on retry/resume, already-written bytes for that segment are not re-downloaded; the download continues from the correct offset.
- Destination path collides with an existing file, or the disk is full/unwritable → the download is marked `Failed` with a readable error, and the rest of the queue keeps running (one bad download doesn't take down the process).
- Handoff request (used by Task 8, consumed later by the extension plan) is malformed, missing its token, or has an unparseable body → the server returns a 400/401 and does not insert a bogus entry into the queue or crash the resident process.
- A download's header/cookie payload is absent (a plain link that needs no auth) → the engine proceeds using only the URL; headers are optional everywhere, never required.

## Task 8: Local handoff HTTP server (pairing + /downloads)

**Files:**
- Create: `src-tauri/src/server/mod.rs`
- Modify: `src-tauri/src/main.rs`
- Test: `src-tauri/tests/handoff_server.rs`

**Interfaces:**
- Consumes: `QueueManager::add` (Task 6), `DownloadRequest` (Task 2).
- Produces:
  - A constant `pub const HANDOFF_PORT: u16 = 57431;` (`server`), bound to `127.0.0.1` only.
  - `pub struct PairingState` with `pub fn new(token_file: std::path::PathBuf) -> Self` (generates and persists a random 32-byte hex token via `rand` on first run if `token_file` doesn't exist, otherwise loads it), `pub fn token(&self) -> String`, `pub fn is_paired(&self) -> bool`, `pub fn mark_paired(&self)`.
  - `pub fn router(queue: std::sync::Arc<QueueManager>, pairing: std::sync::Arc<PairingState>) -> axum::Router` (`server`) exposing:
    - `GET /ping` → `200 "ok"`, no auth, always available.
